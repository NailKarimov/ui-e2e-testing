ui-e2e-testing · OWASP Juice Shop v20.3.0

UI end-to-end: магазин глазами покупателя

UI end-to-end: the shop through a customer's eyes

Тесты Playwright проходят OWASP Juice Shop так же, как человек: ищут товар, кладут в корзину, оформляют заказ, находят его в истории. Всё, что не проверяется, готовится через API; все суммы сверяются с ценами самого магазина; каждый тест идёт на пяти браузерах и устройствах.

Playwright tests walk through OWASP Juice Shop as a person would: find a product, fill the basket, check out, find the order in the history. Whatever is not under test is prepared over the API; every total is checked against the shop's own prices; every test runs on five browsers and devices.

01

Лестница локаторов

The locator ladder

Page Object ищет элемент так, как его находит пользователь и скринридер: по роли и доступному имени. Ниже по лестнице спускаемся, только если приложение не даёт имени, и тогда это дефект доступности с номером. Выберите элемент.

A Page Object finds an element the way a user and a screen reader do: by role and accessible name. We go down the ladder only when the app gives no name, and then it is an accessibility defect with an id. Pick an element.

02

Вход без формы: три ячейки

Login without the form: three slots

Фикстура логинится через API и кладёт сессию прямо в браузер. Juice Shop держит её в трёх местах. Включайте ячейки и смотрите, что увидит тест. Обычный storageState несёт только первые две.

The fixture logs in over the API and puts the session straight into the browser. Juice Shop keeps it in three places. Switch the slots and see what the test would get. A plain storageState carries only the first two.

await context.addCookies([{ name: 'token', value: a.token, url }]);
await context.addInitScript(([token, bid]) => {
  localStorage.setItem('token', token);
  sessionStorage.setItem('bid', String(bid));   // not part of storageState
}, [a.token, a.bid]);
03

Путь покупателя как чек

The purchase journey as a receipt

Смоук-тест проходит весь путь через UI. Ожидаемые суммы он не знает заранее: берёт цены из API и считает сам. Пройдите шаги.

The smoke test walks the whole journey through the UI. It does not know the totals in advance: it takes prices from the API and does the sum itself. Step through it.

04

Один Page Object, два экрана

One Page Object, two screens

Тест вызывает nav.logout() и не знает, на чём он запущен. На компьютере кнопка «Account» в верхней панели, на телефоне её нет: выход живёт в боковом меню.

The test calls nav.logout() and doesn't know what it runs on. On a desktop "Account" is in the top bar; on a phone it isn't: logout lives in the side navigation.

05

Стол повторов: flaky не прячется

The retry desk: flaky doesn't hide

В CI тест получает до двух повторов, локально — ни одного. Нажимайте на попытки, чтобы сделать их зелёными или красными, и смотрите, как Playwright это назовёт.

In CI a test gets up to two retries, locally none. Click the attempts to make them pass or fail and see what Playwright calls the result.

06

Полка дефектов

The defect shelf

Каждый тест утверждает правильное поведение и помечен test.fail(). Пока дефект есть, прогон зелёный; когда его починят, тест покраснеет с «Expected to fail, but passed», и метку надо снять.

Each test asserts the correct behaviour and is marked test.fail(). While the defect is there the run is green; when it is fixed the test turns red with "Expected to fail, but passed" and the marker comes off.

07

Ловят ли тесты баги

Do the tests catch bugs

По одному багу в собранный фронтенд магазина (main.js), полный прогон на Chromium. M5 — наоборот, починка известного дефекта: тест с test.fail() должен это заметить.

One bug at a time in the shop's built frontend (main.js), a full Chromium run. M5 goes the other way, fixing a known defect: the test.fail() test must notice.
