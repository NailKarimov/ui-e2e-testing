# Accessibility testing

WCAG 2.2 level AA on OWASP Juice Shop, in four layers: two automated engines that check the markup, keyboard
tests that use the shop the way a keyboard user does, a reflow test at 320 px, and a manual checklist for what no
tool can judge. Automated tools find roughly a third of real accessibility problems; the rest needs people.

| Layer                             | Where                                            | Runs                            |
| --------------------------------- | ------------------------------------------------ | ------------------------------- |
| axe-core, 12 screens              | `tests/a11y/axe.spec.ts`, `src/a11y/axe.ts`      | every push, Chromium + Pixel 7  |
| Pa11y (HTML_CodeSniffer), 6 pages | `.pa11yci.js`, `scripts/pa11y-summary.mjs`       | every push, as a second opinion |
| Keyboard only                     | `tests/a11y/keyboard.spec.ts`, `src/keyboard.ts` | every push                      |
| Reflow at 320 px                  | `tests/a11y/reflow.spec.ts`                      | every push                      |
| Manual checklist                  | this page, section 5                             | by hand, per release            |

## 1. axe-core with a ratchet

Each screen of the customer journey is opened in its real state (signed in, basket filled, checkout step reached
through the UI) and scanned with the WCAG 2 A/AA, 2.1 and 2.2 AA rules. A plain "zero violations" check would be
red forever on a shop with known problems, and "ignore everything we know" lets new problems slip in behind them.
So the test is a **ratchet**:

- every serious or critical node is matched against `KNOWN_A11Y` (rule + a pattern for the element);
- an unmatched node fails the test: **something new broke**;
- a known defect that is expected on this screen but no longer found also fails: **it was fixed**, so the entry
  is removed and the list can only get shorter;
- a known defect that turns up on a screen where it was not expected fails too: it spread.

Some findings depend on data or timing and are allowed (`may`) rather than required: the "Only 1 left" ribbon
exists only while stock is low, the language notice pops up on some first visits only, and on a phone the
low-contrast e-mail sits on a lighter card and passes. Every scan attaches axe's full JSON to the report, and
moderate/minor findings go to an annotation.

Before scanning, the test waits until all CSS animations have finished: a card still fading in has a lower
contrast than at rest, and the first version of this suite flagged it.

## 2. Pa11y as a second opinion

Pa11y runs HTML_CodeSniffer, a separate implementation of WCAG. `scripts/pa11y-summary.mjs` sorts every error
into **known** (the same defect id as axe, or a Pa11y-only one), **false positive** (reviewed by hand, with the
reason) or **NEW**; CI fails only on NEW. What the comparison showed:

| Finding                                                       |     axe     |   Pa11y   | Verdict                                                                                         |
| ------------------------------------------------------------- | :---------: | :-------: | ----------------------------------------------------------------------------------------------- |
| Search field without a name                                   |      ✓      |     ✓     | UI-A11Y-3, both agree                                                                           |
| Carousel photos without alt                                   | ✓ (3 shown) | ✓ (all 8) | UI-A11Y-8; Pa11y also counts the slides off screen                                              |
| Rating slider without a name                                  |      ✓      |     ✓     | UI-A11Y-11                                                                                      |
| Menu icon 2.9:1 on the top bar                                |      –      |     ✓     | UI-A11Y-13: axe skips `aria-hidden` icons, but WCAG 1.4.11 asks 3:1 of icons that carry meaning |
| Basket buttons, radios, e-mail contrast, empty header rows    |      ✓      |     –     | Pa11y only sees guest pages here                                                                |
| Terms link by colour only, carousel not reachable by keyboard |      ✓      |     –     | axe-only rules                                                                                  |
| Hidden focus-absorbing button in the closed side navigation   |      –      |     ✓     | false positive: hidden elements are not exposed                                                 |
| `href="#/register"` "points to a missing id"                  |      –      |     ✓     | false positive: these are routes of a hash-routed app                                           |
| `<input hidden>` without a name                               |      –      |     ✓     | false positive: nobody sees it                                                                  |

Two engines agreeing is strong evidence; where they differ, each difference was looked at and decided once.

## 3. Keyboard only

| Test                                                                                                      | WCAG                     |
| --------------------------------------------------------------------------------------------------------- | ------------------------ |
| Log in: Tab to the fields, type, Enter                                                                    | 2.1.1 Keyboard           |
| Every stop in the top bar shows where the focus is                                                        | 2.4.7 Focus Visible      |
| Change a basket quantity from the keyboard                                                                | 2.1.1                    |
| Check out from basket to confirmation without a mouse: Tab to each radio, Space, Tab to the button, Enter | 2.1.1, 2.4.3 Focus Order |
| Escape closes the account menu and gives focus back to its button                                         | 2.4.3, 3.2.1             |

`tabTo()` presses Tab until the element has focus, the way a person gets there, so an element that cannot be
reached fails with "not reached with 40 Tab presses". `focusShots()` takes a picture of each Tab stop at rest,
reloads the page so Tab starts from the top again, Tabs to each stop and takes the same picture: if the two are
identical, the focus is invisible there (see section 6 for why pictures and not styles). All five pass: Juice
Shop is usable without a mouse, apart from the carousel (UI-A11Y-10).

## 4. Reflow at 320 px

WCAG 1.4.10: at 320 CSS px (a 1280 px screen zoomed to 400 %) content must fit without sideways scrolling.
Juice Shop scrolls inside its content area, not the page, so a check of `document.scrollWidth` passes while the
product cards are cut off by 24 px. The test checks the content area and lists every element sticking out of it
(carousels and tables may scroll in their own box). Login, registration, contact and About Us pass; the product
list does not: **UI-A11Y-14**, pinned with `test.fail()`.

## 5. Manual checklist

What tools cannot judge. The status column says what has really been done; most of these need a person with a
screen reader, which the CI machine does not have.

| Check                                                                                   | How                                       | Status                                      |
| --------------------------------------------------------------------------------------- | ----------------------------------------- | ------------------------------------------- |
| Names make sense when read aloud, not just exist ("Show the shopping cart" vs "button") | NVDA / VoiceOver, Tab through the top bar | to do with a screen reader                  |
| Form errors are announced when they appear                                              | screen reader on the registration form    | to do with a screen reader                  |
| Order of headings tells the page structure                                              | browser headings list (e.g. HeadingsMap)  | to do                                       |
| Zoom to 200 % keeps all text readable and controls usable                               | browser zoom, desktop                     | to do (400 % is covered by the reflow test) |
| Nothing moves or flashes more than 3 times a second; the carousel can be paused         | watch the carousel and snack bars         | to do                                       |
| Language of the page is set (`lang`)                                                    | axe `html-has-lang`                       | automated, passes                           |
| Focus never lands behind a dialog or banner                                             | keyboard, open the welcome banner         | to do                                       |
| Touch targets at least 24 × 24 px (WCAG 2.5.8)                                          | phone emulation, measure the basket +/−   | to do                                       |

## 6. Does it catch anything? (mutation check)

| Id  | Planted change                                                                           | Caught by                                                                       |
| --- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| M7  | Keyboard focus made invisible: `*:focus{outline:none}` and Material's focus layer hidden | keyboard: "every stop in the top bar shows where the focus is", **after a fix** |
| M8  | **Fix** of UI-A11Y-3: `aria-label="Search"` on the search field                          | axe ratchet on all 12 screens: "known defects no longer found"                  |
| M10 | Product prices in a lighter grey                                                         | axe: a new colour-contrast violation on the product list and the summary        |

M7 survived the first version of the focus test, which compared computed styles before and after focus. Hiding
the focus layer with `display: none` does not stop its computed `opacity` from changing on focus, so the styles
"changed" while nothing changed on screen. The test now compares **pictures**: a screenshot of each Tab stop at
rest and focused. Identical pictures mean invisible focus, whatever the CSS says.

## 7. Running it

```bash
npm run test:a11y          # axe, keyboard, reflow
npm run a11y:pa11y         # Pa11y on the guest pages (needs Chrome: puppeteer's, or CHROMIUM_PATH)
node scripts/pa11y-summary.mjs
```
